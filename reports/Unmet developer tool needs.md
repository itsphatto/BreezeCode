# Developers need cheaper ways to verify AI code

The most important under-served need in software and web development is **verifying and reviewing AI-generated changes**: a review surface that shows the intent behind a diff, proof that the code ran, a signal of test quality, and a way to undo it. Developers now use AI daily (73% of AI-tool users in the 2026 Stack Overflow survey) but trust it mainly when they can check it, and only 6.6% trust it for important decisions ([Stack Overflow 2026](https://stackoverflow.blog/2026/10/06/the-results-of-the-2026-developer-survey-are-here/)). Telemetry from 22,000 developers shows the cost: median time in review rose **441.5%** and PRs merged with no review rose **31.3%** between each organization's low- and high-AI periods ([Faros 2026](https://faros.ai/blog/ai-acceleration-whiplash-takeaways)). Two further needs rank just behind it. Reversible agent actions, meaning undo that covers shell commands and external systems, is well documented but backed mostly by anecdotes and incident reports. For web developers specifically, the strongest differentiated gap is a live loop from the rendered page to the source line to the coding agent, with accessibility checked on the rendered result, because 95.9% of top-million home pages fail WCAG checks and the errors are rising. My recommendation is to build the first need, with the undo path as one of its core fields, and to pursue the web runtime loop as the second bet. The ranking is my judgment from the notes; no survey ranks all of these candidates against each other, and several sources are vendors selling into the problem they describe.

## Verification, not generation, is now the bottleneck

Code is cheap to produce and expensive to trust, and the evidence for that is both survey-based and behavioral. In Stack Overflow's 2025 survey, **66%** named "AI solutions that are almost right, but not quite" as their top frustration, **45.2%** said debugging AI-generated code is more time-consuming, and about 46% distrusted AI accuracy against only 3.1% who highly trust it ([Stack Overflow 2025 AI](https://survey.stackoverflow.co/2025/ai)). The 2026 survey shows the same pattern: 93% say source attribution is needed to trust AI answers, and 63% rarely or never let agents run on autopilot ([Stack Overflow 2026](https://stackoverflow.blog/2026/10/06/the-results-of-the-2026-developer-survey-are-here/); [Agents on a leash](https://stackoverflow.blog/2026/05/27/agents-on-a-leash-agentic-ai-remains-mostly-monitored-at-work)). The 2026 trust question was reworded, so the year-over-year trust numbers are not like-for-like, but the conditional-trust finding stands on its own.

The behavioral data points the same way. Faros pairs rising throughput (epics per developer up 66%) with a **441.5%** rise in median review time, a **242.7%** rise in the incidents-to-PR ratio and an **861%** rise in code churn ([Faros 2026](https://faros.ai/blog/ai-acceleration-whiplash-takeaways)). Faros sells engineering analytics and has no independent replication, and GitClear's duplication findings are only available through secondary coverage with conflicting churn figures ([LeadDev on GitClear](https://leaddev.com/ai/code-maintainability-plummets-in-the-ai-coding-era)). The direction is nonetheless consistent across sources. METR's 2025 randomized trial adds a perception gap: developers expected AI to make them 24% faster, measured 19% slower, and still believed they were about 20% faster afterward ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). METR's 2026 follow-up was declared unreliable because many developers refuse to work without AI, so this remains one study, not a settled result ([METR update](https://metr.org/blog/2026-02-24-uplift-update/)).

What the review surface lacks is specific. Agent reasoning is usually discarded once the diff exists, so reviewers reconstruct intent that was never recorded, and a cited study of 1,154 "AI slop" posts concluded review "wasn't built to recover missing intent" ([Addy Osmani](https://addyosmani.com/blog/agentic-code-review/)). Agents can also rewrite assertions to fit broken behavior, and AI-written tests can reach high coverage while killing few mutants, which is why practitioners propose mutation kill-rate gates of 70-80% ([VirtusLab](https://visdom-maturity-matrix.virtuslab.com/guides/development/mutation-testing-agent-validation)). Grassroots demand is visible but modest in size: a Zed request for "PR-style review comments in Git Diff UI that feed into the active agent thread" drew **162 reactions** after being filed in June 2026 ([Zed #59157](https://github.com/zed-industries/zed/issues/59157)), and the surrounding Git cluster (3-way merge 177, branch merging 167, line staging 158) is the largest recent unmet theme in a modern editor ([Zed #34813](https://github.com/zed-industries/zed/issues/34813)). Context compounds the problem: 85% of developers say project goals and requirements are the most trusted context for AI, and 63% report incomplete information at work ([Stack Overflow 2026](https://stackoverflow.blog/2026/10/06/the-results-of-the-2026-developer-survey-are-here/); [Stack Overflow 2026 survey](https://survey.stackoverflow.co/2026/)). Counter-evidence exists: one arXiv paper found Claude-authored Python tests broadly comparable to human tests under mutation testing, and AI review bots are widespread, with GitHub Copilot review past 60 million reviews, yet developers do not treat bot comments as authoritative ([Addy Osmani](https://addyosmani.com/blog/agentic-code-review/)). The gap is therefore not "no AI reviewer" but "no surface that assembles intent, evidence and test quality next to the diff."

## Agent actions are still not reliably reversible

The second-ranked need is undo that matches what agents actually do. Claude Code's checkpoint feature tracks only edits made through its own file-editing tools; changes from Bash commands such as rm, mv and cp, changes made outside the tool, and subagent edits cannot be rewound, and the official advice is to commit to git first ([Claude Code docs](https://code.claude.com/docs/en/checkpointing)). Users report that auto mode steers the model toward editing files via Bash, which silently bypasses checkpointing ([issue 94657](https://claudeissues.com/issue/94657-bug-auto-mode-tells-the-model-to-edit-files-via-bash-which-silently-disables-che)). The consequences reach beyond files: in April 2026 a Cursor agent reportedly deleted a startup's production database and its volume-level backups in a single API call using a broadly scoped token ([TechSpot](https://www.techspot.com/news/112207-ai-coding-agent-running-claude-wiped-startup-database.html)), following Replit's 2025 incident ([eWeek](https://www.eweek.com/news/replit-ai-coding-assistant-failure/)). One tracker counts nine publicly documented agent data-destruction cases in fourteen months ([Aviatrix](https://aviatrix.ai/threat-research-center/ais-so-smart-keep-deleting-production-databases-2026/)).

Developers already compensate by hand: 60% block agents from altering systems without approval ([Agents on a leash](https://stackoverflow.blog/2026/05/27/agents-on-a-leash-agentic-ai-remains-mostly-monitored-at-work)). I rank this below verification because its demand evidence is weaker, since it rests on a handful of widely reported incidents, one founder's own account, and issue-tracker posts rather than vote counts or survey percentages. It also does not affect every developer daily the way review does. It is, however, the clearest example of a documented, unsolved capability, and it fits naturally into the same artifact as review: a per-change record that states the intent, the evidence, and exactly how to roll the change back, including what cannot be rolled back.

## Web developers lack a live loop from rendered page to source to agent

For web work specifically, the best-evidenced severity signal is accessibility. The WebAIM Million 2026 found **95.9%** of home pages with detectable WCAG 2 failures, up from 94.8%, with an average of **56.1 errors per page** (up from 51), and it links the rise to AI-assisted coding and "vibe coding" ([WebAIM Million](https://webaim.org/projects/million/)). Six error types, led by low contrast (83.9%) and missing alt text (53.1%), account for 96% of detected errors and have led for seven years, which means they are exactly the kind a tool could catch during editing. Today's in-editor tooling is static: Deque's axe Linter analyzes code but cannot judge rendered behavior ([Deque](https://www.deque.com/axe/linters/)), and Interop 2026 lists consistent accessibility trees across browsers only as an "investigation effort" ([web.dev](https://web.dev/blog/interop-2026)).

The second half of the gap is tracing a rendered element back to its source. Chrome DevTools' AI assistance works on the inspected DOM element and does not map nodes to framework components or source files, and Chrome is deprecating automated styling fixes in favor of a "copy to coding agent" hand-off ([Chrome DevTools AI assistance](https://developer.chrome.com/docs/devtools/ai-assistance/chat); [What's new in DevTools 149](https://developer.chrome.com/blog/new-in-devtools-149)). Mapping exists only as per-framework plugins such as LocatorJS and react-dev-inspector, and a Cursor forum thread asks for click-to-source from the built-in browser ([Cursor forum](https://forum.cursor.com/t/click-to-source-from-browser-visual-editor-inspect-open-file-line/146166)). Indirect demand is moderate: debugging was named by 2,159 State of JS 2025 respondents (21.5% of 10,038), and Chrome made its DevTools MCP server stable in June 2026, which signals that the integration point is open to editors that host agents ([State of JS 2025](https://2025.stateofjs.com/en-US/usage/); [DevTools 149](https://developer.chrome.com/blog/new-in-devtools-149)). This rank carries a caveat the others do not: the notes themselves describe combining the a11y and DOM-to-source gaps as the researcher's synthesis, not a sourced claim, and no independent data quantifies time lost to DOM-to-source navigation. Severity evidence is high; evidence that developers are asking for this exact feature is thin.

Several popular-sounding needs did not survive scrutiny. VS Code's all-time most-reacted open requests are personalization and workspace-model asks, such as workbench font size at 4,844 reactions and mouse shortcuts at 2,565, but they are 10-11 years old, are about configuration architecture and are not a niche capability a new tool could own ([VS Code #519](https://github.com/microsoft/vscode/issues/519)). The newest mass-reaction VS Code issues concern control and opt-out (BYOK models, reverting the new UI), which signals a demand for choice, not for a new feature ([VS Code #318545](https://github.com/microsoft/vscode/issues/318545)). On the web side, cross-browser pain has narrowed: browser support is only about 10% of State of CSS pain-point mentions, and Interop 2026 and Baseline already cover the shortlist of new features such as anchor positioning ([State of CSS 2025](https://2025.stateofcss.com/en-US/usage/); [web.dev Interop 2026](https://web.dev/blog/interop-2026)). The largest quantified pain of all, organizational friction such as unclear priorities (16.6% in Stack Overflow 2026) and 10+ hours a week lost to non-coding work (50% in Atlassian's vendor survey), is real but is not something an editor feature can fix ([Stack Overflow 2026 Work](https://survey.stackoverflow.co/2026/work); [Atlassian](https://www.atlassian.com/blog/developer/developer-experience-report-2025)).

## What to build, and what the evidence cannot yet say

Build the review and verification surface first. It sits at the intersection of the strongest evidence in every research stream: survey pain (66% and 45.2% frustration), conditional trust (only 6.6% trust AI for important decisions), measured system effects (review time up 441.5%), and grassroots demand (Zed's agent-feeding review request). It is also poorly served by what exists: AI review bots comment on diffs but do not record intent, show execution proof, or score test quality, and the Stack Overflow 2025 data show developers do not want more AI sprinkled everywhere, since lack of AI integration was the least-cited reason to reject a tool ([Stack Overflow 2025 Work](https://survey.stackoverflow.co/2025/work)). A concrete scope: one record per agent change containing the stated intent and rejected alternatives, evidence such as test output and a run result, a mutation-based test-quality indicator, and a rollback path that explicitly marks shell and external effects as non-reversible. This design folds ranks 1 and 2 into a single artifact, which the notes independently suggest, because context loss, spec drift, review and rollback all point at the same missing layer.

The second bet, for a web-focused product, is the live-page loop (rank 3). It is the only candidate where a differentiated, web-specific wedge coincides with a measured and worsening problem, and Chrome's own decision to hand styling work to external coding agents leaves the integration point to editors. It should be treated as a hypothesis to test, not a proven demand: validate it by checking whether developers who inspect elements in an agent-hosting IDE actually ask for source mapping and a11y verification.

The evidence has real limits. Reddit could not be accessed, so no theme has Reddit confirmation. Hacker News wish threads from 2025-2026 are small, and no high-engagement dedicated "wish" thread was found. No source quantifies how often debugging AI code beats writing it by hand, and the "perception gap" rests on a single small METR trial. Several statistics could not be traced to primary sources (a "96% distrust" figure and a "61% of agent PRs unreviewed" figure) and are excluded here. Vendor-run sources (Faros, Atlassian, Endor Labs, Augment, GitGuardian, Veracode) have a commercial interest in the problems they measure, and Stack Overflow's self-selected sample leans toward its own community.

## Conclusion

The research changes the question from "what feature is missing?" to "which layer of the workflow has not caught up with generation." Developers are not asking for more AI: they are asking for ways to confirm, bound and undo what it did, and every independent signal, from survey frustration to review-time telemetry to feature requests, converges on the review step. The web-specific finding is that the strongest severity evidence (rising accessibility failures tied to AI-assisted code) has no matching grassroots request, which suggests the need is latent and the opportunity is in making rendered-page feedback part of the same loop the agent and the developer already share.

A practical implication follows. A single per-change record that couples intent, evidence and rollback should satisfy more of the ranked needs than any separate feature would, and it should be measured against outcomes (rework, churn, incidents) and not against self-reported speed, since the one controlled study shows self-reports can miss by roughly 40 percentage points (a 24% expected speedup against a measured 19% slowdown). Until a first-party 2026 productivity study or a Reddit pass is added, treat the ranking as the weight of reports, not a market measurement.
